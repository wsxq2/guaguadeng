## 职责规划

按实现进度创建模块，不预先建立空目录：

- `domain/`：卡牌、玩家与回合状态、合法性、判胜和计分。
- `engine/`：统一处理出牌动作，推进轮、局和场，保证失败不改变状态。
- `strategies/`：从合法动作中选择，供 AI、提示和托管复用。
- `ui/`：展示与交互，不修改规则状态；界面采用 PySide6 + QML / Qt Quick。

## 模型与命名

以下是职责边界，不要求一次建立全部类型；具体字段和接口随测试逐步确定。

| 类型或模块 | 职责 |
| --- | --- |
| `Card` | 不可变的牌值对象，包含点数和花色；相等性包含花色，出牌大小由规则判断 |
| `Player` | 用稳定 ID 标识玩家，保存手牌、获牌和累计积分；真人和 AI 共用模型 |
| `RoundState` | 表示一轮，保存领牌者和按顺序排列的出牌记录 |
| `GameState` | 保存玩家、本局庄家、当前轮和游戏阶段，承载跨局累计状态 |
| `rules.py` | 用纯函数实现出牌验证、合法动作枚举、判胜和计分，不修改输入状态 |
| `GameEngine` | 对外提供统一操作入口，检查阶段、行动顺序和牌的归属，调用规则并推进状态 |
| `Strategy` | 用统一接口从合法动作中选择出牌，供 AI、提示和托管复用 |

使用 `RoundState` 对应规则中的“轮”，不使用较生僻的 `TrickState`。
`RoundState` 是数据模型，不因方法少而合并进引擎。当前行动者、跟牌数量等可推导信息尽量不重复存储。
判胜放在规则模块中；当前轮之外的历史记录按后续实际需求增加。

当前没有独立账号资料模型，因此使用简洁的 `Player`，暂不拆成 `PlayerProfile` 和 `PlayerState`。
规则目前只有一个版本且没有内部状态，先使用 `rules.py` 函数，不建立 `Rule` 或 `Rules` 类。

## 设计原则

- `Card` 采用值对象思路，`Player` 采用实体思路；两者的身份语义不同。
- `GameEngine` 提供少量公开操作，集中处理状态变化；失败不能留下部分修改，局末只能结算一次。
- 游戏阶段先用枚举和明确的转换表达有限状态机，不预先为每个阶段创建状态类。
- `Strategy` 采用策略模式，可替换随机、启发式或搜索策略；接口接收该玩家可见的信息及合法动作，不暴露对手手牌。
- 控制层获取策略选择后，通过引擎的统一出牌入口提交；引擎仍执行验证，不信任调用方。
- 真人的异步界面输入不必包装为同步策略。
- 界面更新可采用事件或观察者方式，具体机制随界面技术确定；不提前引入通用事件框架。
- 新代码不依赖或导入 `legacy/`。旧版保留到新实现可用，再决定移除。

## 测试驱动开发

`Rules.md` 是规则规范，测试用例是可执行的规则示例，不再单独维护 `rule_examples.md`。
每次围绕一个小行为执行“写测试 → 确认预期失败 → 最小实现 → 测试通过 → 重构”。
测试验证公开行为，不绑定私有方法或预设类结构；同时覆盖允许与拒绝的出牌。

按以下顺序推进：

1. 卡牌与牌组：40 张唯一牌、合法点数与花色；花色影响牌的身份，不影响压牌大小。
2. 领牌与拆牌：1～4 张同点数牌、允许拆分、禁止非法数量和混合领牌。
3. 普通跟牌：数量一致、配型优先、能压必须压、无法压牌时的自由选择范围。
4. 第三人管牌：正常管牌可选、只能压低牌时必须最大、无法压牌时按规定牌型任选。
5. 判胜与计分：同点数先出者胜、混合牌不能赢、只获自己的牌和积分变化。
6. 引擎：行动顺序、失败不改变状态、轮庄、跨局累计、结算唯一、中途结束及完整一局的牌数守恒。
7. 完成新界面，再增强策略与动画。

从 `Card`、必要的 `RoundState` 数据和规则函数开始，用构造局面测试规则，不依赖完整引擎或 GUI。

## 当前接口与生命周期

- `validate_lead(hand, cards)`：保留独立领牌入口。
- `validate_play(hand, cards, round_state)`：自动根据轮内记录验证领牌、普通跟牌或第三人管牌。
- 两种验证均返回不可变 `ValidationResult`，`.is_valid` 表示合法性，`.error` 为 `PlayError` 或 `None`。不会修改输入。
- `legal_plays(hand, round_state)`：枚举所有合法实际卡牌组合，保留不同花色和拆牌选择。
- `determine_winner(round_state)`：返回当前领先玩家 ID；轮完成时即胜者，空轮返回 `None`。
- `calculate_score(won_count)`：返回本局积分变化。

规则函数接收合法牌组与合法轮内历史，验证待提交动作；不充当任意外部状态的反序列化校验器。

`GameEngine` 通过 `submit_play(player_id, cards)` 统一提交动作。验证失败时返回原因并保留原状态；成功时自动推进一轮，记录获牌，或在最后一轮结算本局。阶段或顺序错误也通过 `ValidationResult` 返回。

状态中的玩家、出牌、手牌、历史均使用不可变对象和元组。`snapshot()` 返回完整只读快照，旧快照不随游戏推进改变。获牌是出牌历史的计分引用，不应在牌数守恒检查时重复计数。

- 初始化或 `start_session()`：进入 `READY`，各玩家 100 分；显式新建一场会放弃旧场。
- `start_next_game()`：从 `READY` 或 `FINISHED` 进入 `PLAYING`；其他阶段调用抛出 `ValueError`。
- 最后一轮完成：先记录胜者获牌，再结算一次，进入 `FINISHED`；最后一轮保存在 `completed_rounds`，当前轮为 `None`。
- `end_session()`：进入 `ENDED`，保留已结算积分，不结算未完成局；重复调用无副作用。
- 座位 ID 0、1、2、3 对应东、北、西、南，按逆时针递增。庄家与每轮领牌者分开保存。
- 构造引擎时可注入 `random.Random(seed)`，便于复现洗牌和首局庄家。

完整快照包含所有手牌，供可信控制层使用；策略必须通过 `observe(state, player_id)` 构造仅含该玩家可见信息的视图，不能直接把完整快照交给 AI。

## 后续工作

下一阶段使用 PySide6 + QML / Qt Quick 实现界面和控制器，将观察信息映射到显示，管理 AI 延迟与任务失效。当前随机策略仅作为可玩的基线，不包含智能评估。

## 玩家观察与策略接口

- `domain/observation.py` 的 `observe(state, player_id)` 按白名单提取数据，返回不可变 `PlayerObservation`。无效 ID 抛出 `ValueError`。
- 观察对象仅包含自己的手牌、各玩家 `PublicPlayerInfo`、庄家、阶段、当前轮和本局已完成轮。不会保存原始 `Player` 或 `GameState` 引用。
- 公开玩家信息含 ID、名称、剩余牌数、获牌及累计积分；历史保留轮的顺序与内部出牌顺序。下一局历史清空，积分保留。
- 策略使用 `Strategy` Protocol：`choose_play(observation, legal_plays)`。实现同名方法即可，不强制继承。
- 控制层只在游戏进行中、轮到该玩家时调用策略；从观察中的本人手牌和当前轮计算合法候选，再交给策略。
- `RandomStrategy` 支持注入独立的 `random.Random`，对实际卡牌组合均匀抽样，暂不使用历史。空候选抛出 `ValueError`，不使用空出牌伪装为跳过。
- 选出的动作仍通过引擎再次验证。该结构防止意外泄露，不是隔离恶意代码的安全沙箱。

## 正式对局控制器

`ui/controller.py` 的 `GameController` 已实现，真人固定为南侧（ID 3），其余座位使用随机策略。尚未接入正式 QML 牌桌，当前启动入口仍为交互验证页。

- QML 属性：`cards` 仅含真人手牌；`players` 仅含公开积分、剩余牌数、获牌数、庄家和行动标识；另有 `phase`、`gameNumber`、`humanTurn`、`hasSelection`、`message`。
- 操作：`startNextGame`、`toggle`、`clear`、`hint`、`submit`、`endSession`、`newSession`。结束本场后才能重开一场，积分由引擎管理。
- 单次 QTimer 默认间隔 700 毫秒，每次执行一个 AI 动作；结束本场即停止计时。AI 仅接收自身观察及合法候选。
- `roundPlays` 在新轮尚无人出牌时保留上轮结果，`showingPreviousRound` 标识该情况，供界面明确标注。新轮首次出牌后显示新轮。
- 提示只选取一组合法牌，优先较少张、较小点数，不承诺最优策略。

下一步实现正式 QML 牌桌并连接该控制器，再切换桌面及 Android 启动入口，进行真机验收。
